# Runtime с HTTPS-координатором

Целевой сценарий подключения к координатору и управления своими устройствами
через панель без CLI описан в [WEB_UX.md](WEB_UX.md). Ниже описана текущая
реализация, включая пока необходимые операции регистрации и настройки через CLI.

`portal` объединяет запуск агента, CLI и веб-панель в одном бинарнике.
Крейт `portal-runtime` — встроенная библиотека, отдельный исполняемый файл
не требуется. Агент использует HTTPS API координатора через `portal-net`,
получает карты long polling, назначает своему TUN выданные
IPv4 /32 и IPv6 /128, устанавливает host-маршруты и применяет TCP-разрешения
в WireGuard workers. Координатору не нужны TUN или root.

## Первый запуск

### Запуск без параметров

```sh
cargo build -p portal-cli
sudo target/debug/portal web
```

`portal web` выдаёт ссылку для входа в работающий агент. Если локальный API
не слушает порт, команда без дополнительных флагов запускает runtime в этом же
терминале; токен заранее создавать не нужно. Откройте выведенную ссылку в браузере.
Терминал должен оставаться открытым, `Ctrl+C` останавливает агент.
`sudo target/debug/portal` без аргументов делает то же самое.

Для явного запуска используйте `sudo target/debug/portal start`; параметры
задают запуск агента, например `portal start --config PATH`.
Для переноса приложения достаточно одного файла `portal`.

`portal run` — синоним `portal start`. Если существует
`/etc/portal/runtime.json`, агент читает его для управляемого запуска.
Если файла нет, используются значения ручного режима:

| Параметр | По умолчанию |
|---|---|
| TUN-интерфейс | `portal0` |
| Приватный ключ | `/etc/portal/device.key` |
| UDP-сокет WireGuard | `0.0.0.0:51820` |
| Веб-панель и HTTP API | `127.0.0.1:51821` |
| Токен локального API | `/run/portal.token` |
| Адреса TUN | Пустой список; задаются через `--address` |
| MTU | `1420` |
| Workers | Число доступных CPU, максимум `256`; при ошибке определения — `4` |
| Порог рукопожатий | `100` в секунду до запроса cookie |
| Dual stack | Включён |
| Автоматические маршруты | Включены |

На первом ручном запуске отсутствующий ключ создаётся случайным и сохраняется
с правами `0600`; новые каталоги ключа создаются с правами `0700`. При рестарте
ключ остаётся прежним. Существующий повреждённый файл не перезаписывается.
В управляемом режиме отсутствующий ключ требует восстановления или явного
создания новой идентичности через `keygen`/`enroll`.

Для входа получите ссылку командой `portal web`.
Чтобы изменить параметр ручного запуска, достаточно указать его одного:

```sh
sudo target/debug/portal run --tun test0 --listen 0.0.0.0:51900
```

Явные флаги ручного режима выбирают ручной запуск; автоматическое чтение
`/etc/portal/runtime.json` при этом не выполняется. `--config PATH` выбирает
управляемый режим и не совмещается с ручными флагами. Ошибка существующего
конфига не приводит к переключению в ручной режим.

### Подключение к координатору

Соберите workspace и запустите [координатор](COORDINATOR.md). Для runtime нужны
Linux, `iproute2` и права на создание TUN и настройку сети. Ниже агент работает
от root; его файлы состояния также должны принадлежать root.

```sh
cargo build --workspace
sudo install -d -m 700 runtime-state
sudo target/debug/portal keygen --private-key-file runtime-state/device.key
printf '{}\n' | sudo tee runtime-state/policy.json >/dev/null
sudo chmod 600 runtime-state/policy.json
sudo install -m 600 /path/to/user.token runtime-state/user.token
```

Токен пользователя выдаётся при регистрации на координаторе. Для учётной записи
`admin` он находится в `STATE_DIR/admin.token`. Он нужен только для регистрации
устройства: не сохраняйте его в конфигурации агента.

Отредактируйте [runtime/example.json](../runtime/example.json):

- `coordinator.url` — доступный устройству HTTPS origin без пути, query и пароля;
- `device_name` — имя устройства;
- `endpoints` — необязательные явно заданные UDP-адреса **этого** устройства;
  LAN-адреса агент добавляет автоматически;
- `stun_servers` — необязательные дополнительные STUN-серверы в формате `IP:PORT`;
  встроенный STUN координатора агент находит автоматически по карте сети;
- `ca_file` — доверенный сертификат/CA для разработки или частного центра
  сертификации. При отсутствии поля используются системные корни доверия;
- пути к ключу, credentials, политике, сохранённой карте и токену локального API.
  Относительные пути разрешаются от каталога JSON-конфига.

Все поля JSON можно опускать: верхний уровень получает те же значения
интерфейса, ключа, MTU, API и флагов, что приведены выше. Для секции
`coordinator` используются:

| Поле | По умолчанию |
|---|---|
| `url` | `https://localhost:8443` |
| `device_name` | `my-device` |
| `credential_file` | `/etc/portal/device.json` |
| `policy_file` | `/etc/portal/policy.json` |
| `map_file` | `/etc/portal/network-map.json` |
| `ca_file` | Не задан, используются системные корни доверия |
| `endpoints` | Пустой список |
| `stun_servers` | Пустой список дополнительных серверов; используется STUN координатора |

Даже `{}` является конфигом управляемого режима с этими значениями. Для работы
нужны доступный координатор, его TLS-доверие и настоящие credentials устройства;
регистрация остаётся отдельным действием. У `enroll` значения флагов по умолчанию:
`--config /etc/portal/runtime.json` и `--user-token-file /etc/portal/user.token`.
При первой регистрации отсутствующий ключ создаётся автоматически. Повторная
регистрация не заменяет существующие credentials или потерянный ключ устройства.
`keygen` без флагов создаёт `/etc/portal/device.key` и отказывается перезаписывать
существующий файл.

`listen` задаёт локальный UDP-сокет. Агент раз в 30 секунд обновляет кандидаты:
явно заданные `endpoints`, наблюдения STUN и адреса активных LAN-интерфейсов.
Всего публикуется до восьми адресов; явно заданные адреса имеют приоритет.
Адреса самого Portal-интерфейса и IPv6 link-local не публикуются. При явной
привязке `listen` к одному IP автоматически публикуется только этот локальный IP.
STUN использует тот же сокет и фактический порт, что WireGuard, включая `listen`
с портом `0`. Внешний порт берётся из ответа сервера и может отличаться от локального.
STUN Binding реализован по [RFC 8489](https://www.rfc-editor.org/rfc/rfc8489.html),
с проверкой адреса сервера, случайного transaction ID, срока и границ сообщения.
Координатор содержит собственный STUN-сервер. Его параметры приходят в проверенной
HTTPS-карте (`stun.port`, `stun.endpoints`); ручной `stun_servers` не нужен.
По умолчанию агент использует IP-адреса HTTPS-имени координатора и опубликованный
UDP-порт. Например, при координаторе `https://vpn.example:8443` по умолчанию
нужны TCP/8443 и UDP/8443. DNS-имена разрешаются заново при циклах discovery.
При NAT или отдельном UDP-порте сервера задайте `stun.listen` и `stun.endpoints`
в конфигурации **координатора**, чтобы все агенты получили настройку автоматически.
Дополнительные внешние наблюдения можно включить через `coordinator.stun_servers`
на агенте. Если STUN на сервере явно отключён, без дополнительных серверов
остаётся поиск LAN и явно заданных кандидатов. Карты старого координатора без
поля `stun` также поддерживаются.
UPnP/PCP port mapping и реле пока отсутствуют. Прямой путь не гарантируется при
симметричном NAT или блокировке UDP; команда вернёт ошибку, а агент продолжит попытки.
Координатор отклоняет P2P-согласование, пока оба устройства не опубликуют кандидаты.

```sh
sudo target/debug/portal enroll \
  --config runtime/example.json --user-token-file runtime-state/user.token
sudo target/debug/portal run --config runtime/example.json
```

`enroll` отправляет публичный WireGuard-ключ токеном владельца и сохраняет
отдельные credentials устройства в `credential_file`. Приватный ключ остаётся
локально. Существующий файл не перезаписывается; обычный рестарт не регистрирует
устройство заново. При потере credentials владелец может отозвать устройство
или заменить его токен через API координатора. Ошибка сохранения после успешной
регистрации также требует такого восстановления через API.

Каталоги состояния должны иметь права `0700`, credentials, политика и карта —
`0600`, все от имени пользователя, запускающего агент. Карта сохраняется атомарно;
symlink вместо приватного файла отклоняется. Lock запрещает два процесса с одним
файлом credentials. После регистрации копия пользовательского токена агенту не нужна.

## Разрешения на устройстве

По умолчанию `policy.json` содержит `{}`. Чтобы разрешить конкретному устройству
TCP/8080 на этом устройстве назначения, запишите:

```json
{
  "ПУБЛИЧНЫЙ_WG_КЛЮЧ_ИСТОЧНИКА_64_HEX": { "tcp": [8080] }
}
```

Используйте настоящий ключ зарегистрированного устройства, например выведенный
его `keygen`. Право направлено: оно не открывает обратное подключение и другие
устройства владельца. Ответы разрешённого TCP-соединения проходят после
наблюдения SYN → SYN/ACK → ACK, отдельное обратное правило для них не нужно.

Агент перечитывает файл раз в секунду. Заменяйте файл целиком атомарным rename,
сохраняя владельца и права. Сначала применяются локальные ограничения, затем
агент публикует политику с ревизией. Новое разрешение начинает работать после
подтверждения активной привязки пира в карте координатора. Локальный отзыв
закрывает соответствующие потоки и при недоступном координаторе. Ошибка чтения
или формата политики блокирует трафик и останавливает агент.

При изменениях workers и применение карты используют общий gate. Агент очищает
ожидающий plaintext в BoringTun до включения новых правил, удаляет отозванных
пиров и инвалидирует больше не разрешённые TCP-потоки. Подходящие действующие
WireGuard-сессии и потоки сохраняются; обычное продление lease их не сбрасывает.
Ошибка применения карты закрывает доступ и запускает очистку ресурсов агента.
Установленные другими процессами маршруты агент не удаляет.

Ограничения первой версии: только TCP, без IPv4 options, фрагментов, IPv6 extension
headers и TCP Fast Open. UDP и ICMP через управляемый туннель блокируются.
Проверяются ключ, адрес источника, адрес назначения и разрешение потока;
одного флага ACK недостаточно. Это ACL, а полную проверку TCP выполняет стек ОС.
Таблица ограничена 8192 потоками на устройство: установление — 30 секунд,
простой — 300 секунд, закрытие после FIN — до 30 секунд. Для длительно
бездействующих соединений приложению нужен TCP keepalive с интервалом меньше
300 секунд. Exit node ещё не реализован.

## P2P-запрос и диагностика

### Локальная веб-панель

После запуска агента откройте `http://127.0.0.1:51821/` или адрес из
`api_listen`. Панель встроена в бинарник runtime; отдельный веб-сервер,
Node.js и установка фронтенд-зависимостей для запуска не нужны.

При запуске runtime печатает строку `web panel: http://…/` без секретов,
чтобы токен локального API не попадал в журнал службы. При `api_listen`
с портом `0` выводится фактически выбранный порт. В интерактивном терминале
при запуске выводится готовая ссылка с токеном. Для работающего агента
её также выдаёт явная команда `portal web`. При перенаправленном выводе
первого запуска получите ссылку отдельным вызовом `portal web`.

Чтобы получить готовую ссылку для входа без ручного копирования токена:

```sh
sudo target/debug/portal web
# Для нестандартного адреса или пути:
sudo target/debug/portal web --api 127.0.0.1:51821 --token-file runtime-state/api.token
```

Откройте выведенную ссылку в браузере. Для работающего агента команда печатает
ссылку и завершает работу. Без флагов она также запускает отсутствующий агент;
с явными `--api`/`--token-file` вместо автозапуска показывает инструкцию.
Занятый порт с отсутствующим или неверным токеном не приводит к запуску второго
агента. Браузер от root не запускается. Токен передаётся во фрагменте `#token=…`, который
браузер не отправляет HTTP-серверу. Панель сразу удаляет фрагмент из текущей
записи истории через `history.replaceState` и выполняет вход. Ссылка даёт доступ
к управлению локальным агентом — не передавайте её другим.

Также можно вставить токен из `api_token_file` или выбрать этот файл в форме входа.
Для стандартного ручного запуска токен находится в `/run/portal.token`,
для [примера управляемого запуска](../runtime/example.json) — в
`runtime-state/api.token`.

Панель показывает локальные адреса и ключ устройства, состояние координатора,
оставшееся время карты, пиров, действующие TCP-разрешения и статистику.
Есть поиск и кнопка P2P-запроса к пирам с разрешённым исходящим доступом.
Основные разделы: «Обзор» с выбором пира и запросом подключения,
«Устройства» с поиском по имени, адресу или ключу и «Диагностика» со
счётчиками, состоянием карты и техническими параметрами. В «Параметрах
устройства» доступны endpoint, ключ, keepalive, входящие и исходящие TCP-порты,
пакеты и байты. Кнопка копирования локального публичного ключа находится
в раскрываемых технических параметрах диагностики.
Подключение доступно только в управляемом режиме, при работоспособном агенте,
действующей карте и исходящем TCP-разрешении. Ручной режим позволяет
просматривать настроенных пиров; редактирование остаётся в CLI/API.
Панель не содержит команды отключения, измерения задержки или таймера сессии:
локальный API этих возможностей не предоставляет. При потере связи показаны
последние данные с предупреждением; новый запрос подключения блокируется
до восстановления связи. Наличие endpoint не считается подтверждением пути.
Данные обновляются каждые пять секунд. Панель показывает состояния
`offline`, `probing`, `direct` и актуальный UDP endpoint после roaming.
Успех команды подключения означает проверенный прямой путь.
Разрешения редактируются в панели владельцем. Для прежнего режима без политики
владельца сохраняется публикация из локального файла; после перехода на
желаемые политики агент получает их с координатора, применяет ограничения и
подтверждает ревизию. Локальный файл после этого не перезаписывает решение владельца.

Фронтенд обращается только к локальному HTTP API с того же origin:
`GET /api/v1/snapshot` возвращает структурированное состояние, а
`POST /api/v1/command` выполняет P2P-запрос через `operation: "connect"`.
Оба маршрута требуют bearer-токен. Снимок не содержит приватных ключей,
credentials координатора и путей к секретным файлам. Статические HTML/CSS/JS
доступны без токена; Host/Origin и loopback проверяются для всех маршрутов.

Панель доступна через SSH-туннель с другим локальным портом:

```sh
ssh -L 127.0.0.1:51822:127.0.0.1:51821 root@SERVER
```

Откройте `http://127.0.0.1:51822/`. В ссылке, полученной командой `portal web`
на сервере, замените только порт `51821` на `51822`, сохранив фрагмент токена.
Используется токен локального API **удалённого** агента. Панель управляет именно
этим сервером; его устройства и сетевые подключения не относятся к машине браузера.
Транспортный peer по-прежнему должен быть loopback, `Host` — `localhost`,
`127.0.0.1` или `[::1]`; порт может отличаться от listener. При наличии `Origin`
он обязан совпадать с HTTP origin из `Host`, включая порт. Bearer-токен
остаётся обязательным для API; `X-Forwarded-Host` не используется.

Токен сохраняется в `sessionStorage` этой вкладки; API-запросы передают его только
в заголовке `Authorization`, без query-параметров и cookies.
После обновления страницы панель автоматически проверяет сохранённый
токен и восстанавливает вход. Временная недоступность агента не удаляет токен:
можно повторить подключение без повторного ввода. Выход или ответ API `401`
очищает сохранённый токен и возвращает форму входа. После перезапуска агента
нужен новый токен из его файла.

HTML/CSS/JS встроены в бинарник. После изменения интерфейса пересоберите
`cargo build -p portal-cli --release` и при следующем запуске используйте
обновлённый `target/release/portal`. Браузерная проверка интерфейса:
`python3 runtime/scripts/check-web.py` (нужен Firefox). Она запускает отдельный
браузер и локальный тестовый API, проверяет вход, права, P2P-ответы,
истечение карты, потерю связи, ручной режим и адаптивность без изменения VPN.

### CLI

```sh
sudo target/debug/portal status --token-file runtime-state/api.token
sudo target/debug/portal list --token-file runtime-state/api.token
sudo target/debug/portal connect --device-id DEVICE_ID --token-file runtime-state/api.token
```

Локальный HTTP API принимает `{"operation":"connect","peer_device_id":"DEVICE_ID"}`.
A отправляет намерение координатору; агент B проверяет карту и локальную
политику, запускает проверку кандидатов и отвечает. После ACK агент A тоже
проверяет данные B. Сообщение `signaling=accepted path=direct endpoint=...`
возвращается только после аутентифицированного WireGuard-ответа, подтверждающего
обратный путь. Само HTTPS-подтверждение не переводит путь в `direct`.
Срок P2P-сигнала проверяется по времени координатора из действующей карты
с монотонным отсчётом после её получения; локальная правка политики этот
отсчёт не сбрасывает. Это устраняет преждевременный отказ при небольшом
расхождении системных часов устройств.
Проверки используют обычное [WireGuard-рукопожатие](https://www.wireguard.com/protocol/),
поэтому недоверенный UDP-пакет не может установить соединение или выдать доступ.

Все подходящие кандидаты проверяются одним рукопожатием параллельно с общего
UDP-сокета. Раунд длится до 15 секунд; попытки идут не чаще раза в 5 секунд,
после неудачи следует пауза 30 секунд. Согласование и проверка в команде `connect`
ограничены общим сроком 28 секунд, затем возвращается ошибка; фоновые попытки
продолжаются. Повторный запрос может разбудить следующий раунд. Карта сети уже
содержит кандидаты, поэтому авторизованные пиры соединяются и без команды.

Пиры используют keepalive 25 секунд. `direct` сохраняется до 90 секунд после
последнего аутентифицированного ответа; затем возобновляется перебор кандидатов.
Смена кандидатов запускает новый поиск, не пересоздавая UDP-сокет и сохраняя
действующую WireGuard-сессию. Истечение lease и отзыв доступа блокируют пакетный
путь и проверки соединения. Реле и состояние `relayed` пока не реализованы.

`status` показывает ID устройства/сети, поколение и ревизию карты, ревизию
подтверждённой политики, `policy_pending`, состояние координатора и остаток lease.
При отклонённой публикации локальные ограничения продолжают действовать,
подтверждённая карта обновляется; причина HTTP-ошибки видна в stderr.
Ручные `peer upsert/remove` и `endpoint set/clear` в управляемом режиме запрещены.
Разрешения меняются через локальный файл.

При обрыве HTTPS агент повторяет запросы; действующая карта работает до своего
срока. Проверка срока монотонная и выполняется на пути пакета, включая выдачу
очереди. По истечении срока трафик блокируется; свежая карта восстанавливает
доступ. После сетевой ошибки агент запрашивает карту сразу без ожидания изменений.
Отозванный токен закрывает доступ и завершает процесс.

Сохранённая карта фиксирует идентичность сети, адреса и курсор. На старте
требуется свежий HTTPS-ответ: офлайн-запуск из кеша пока не поддерживается.
Проверяются версия протокола, ключ/владелец/ID устройства, дубли IP и ключей,
возврат ревизии назад и сроки. Подмена идентичности не применяется.

Ручной режим с `run --tun ... --address ...` сохраняется для разработки и
совместимости с обычным WireGuard. В нём разрешения координатора не действуют.

## Проверки

```sh
cargo test --workspace --offline
cargo build --workspace --offline
unshare --user --map-root-user --net python3 runtime/scripts/check-managed.py
unshare --user --map-root-user --net --mount python3 runtime/scripts/check-defaults.py
```

Проверка `check-managed.py` требует разрешённых user namespaces, `ip`, `nsenter`,
`openssl` и Python 3. Создаются два изолированных network namespace, HTTPS-координатор,
два агента и TCP-сервер. Проверяются IPv4/IPv6, согласование, запрет другого порта,
офлайн-отзыв действующего TCP-потока, истечение lease, переподключение и отзыв
устройства. Сетевые настройки хоста не меняются. Обычные unit-тесты также
проверяют очистку очереди перед handshake и сохранение действующей WG-сессии.

`check-defaults.py` также требует `mount` и монтирует временные `/etc` и `/run` только
внутри namespace и проверяет запуск без аргументов, постоянство ключа,
автоматический выбор конфига и явные переопределения параметров.


### Проверка прямого пути

```sh
cargo test --workspace --offline
cargo build --workspace --offline
unshare --user --map-root-user --net python3 runtime/scripts/check-managed.py
PORTAL_TEST_NAT=1 unshare --user --map-root-user --net python3 runtime/scripts/check-managed.py
```

Сквозные проверки требуют `/dev/net/tun`, user/network namespaces, `iproute2`,
`nsenter`, OpenSSL и Python 3; NAT-режиму также нужен `nft`.
Они поднимают временный HTTPS-координатор, два агента и TCP echo-сокеты,
проверяют IPv4/IPv6, ACL, отзыв доступа и истечение lease. NAT-режим добавляет
отдельный маршрутизатор с stateful firewall и SNAT на другой UDP-порт;
внешний endpoint обнаруживается встроенным Rust STUN-сервером координатора,
параметры которого агент получает автоматически через HTTPS. Отдельного
Python-ответчика и ручного `stun_servers` в этой проверке нет. Проверяется также
таймаут при блокировке UDP после успешного ACK и восстановление после разблокировки.
Все сетевые изменения
происходят внутри временных namespaces. Модульный UDP-тест дополнительно проверяет
недоступный первый кандидат и восстановление после смены endpoint.

### Подключение одной сети через панель

Стандартный запуск без ручных флагов подготавливает локальный ключ и защищённый
профиль рядом с ним (`device.profile.json`). До подключения сетевой доступ закрыт.
После локальной авторизации открывается «Сеть и аккаунт»: вход по HTTPS-origin
и токену пользователя или регистрация с именем аккаунта. Служебное имя устройства
можно изменить на шаге добавления и затем в его параметрах. Второй origin
не поддерживается и не заменяет текущий профиль. Явный ручной запуск WireGuard
с параметрами сохраняет прежний режим, без автоматического включения ACL Portal.

Профиль и отдельные credentials/политика/карта/PEM CA сохраняются агентом с `0600`
в каталоге `0700`. Приватный ключ не передаётся браузеру. Обновление страницы
не создаёт ключ, аккаунт или устройство заново; перезапуск агента восстанавливает
сохранённое подключение. Неверный токен аккаунта не завершает локальную сессию.
Утраченные device credentials не вызывают автоматическую ротацию.

Дополнительные локальные API (все требуют прежний local API Bearer и Host/Origin):

| Endpoint | Назначение |
|---|---|
| `GET /api/v1/account` | Состояние аккаунта, собственные устройства, этап добавления |
| `POST /api/v1/account` | Вход `{address, token, ca_pem?}` или регистрация `{address, user_name, ca_pem?}` |
| `POST /api/v1/account/activate` | Добавление/подключение устройства `{name}` |
| `POST /api/v1/account/token` | Явный экспорт пользовательского токена; вне снимков состояния |
| `POST /api/v1/account/device` | `policy`, `save_policy`, `rename`, `revoke` с `device_id`; права проверяет координатор |

Снимок дополнен `setup_available`, ID/именем аккаунта сети и признаком `owned`
для известных пиров. Реестр аккаунта не берётся из device token. Политики имеют
контроль ревизий; фоновые обновления не заменяют черновик редактора.
Массовое применение строки разрешения сначала загружает ревизии всех своих
целевых устройств, исключая источник, затем требует явного подтверждения.
Для каждой цели выполняется отдельный `save_policy` с её исходной ревизией:
остальные источники сохраняются, конфликт не повторяется автоматически,
результат и ACK показываются отдельно. Новые устройства не наследуют правило.
Ответ аккаунта разделяет `error` реестра и `activation_error` применения
локальной сети: неудачный запуск VPN не делает полученный реестр устаревшим.
Карта показывает только известные агенту направления и порты, а присутствие
удалённых агентов остаётся неизвестным. Выход из панели оставляет VPN работающим.
Отдельные отключение/забывание профиля и интеграция GUI-открытия с установщиком
пока остаются задачами из WEB_UX.md.

Проверка реального подключения из панели, восстановления профиля и отзыва
устройства в изолированной Linux-сети (не изменяет `/etc`, `/run` и сеть хоста):

```sh
cargo build -p portal-cli -p portal-coordinator
unshare --user --map-root-user --net --mount python3 runtime/scripts/check-web-network.py
```

Она использует временный HTTPS-координатор и настоящий TUN, проверяет
регистрацию с собственным CA, применение сети без перезапуска, сохранение
ключа/ID, автоматическое восстановление и ACK желаемой политики. После отзыва
устройства панель и пользовательская авторизация остаются доступны.
