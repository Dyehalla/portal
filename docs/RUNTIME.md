# Runtime с HTTPS-координатором

`portal-runtime` остаётся отдельным процессом. Он использует HTTPS API координатора
через `portal-net`, получает карты long polling, назначает своему TUN выданные
IPv4 /32 и IPv6 /128, устанавливает host-маршруты и применяет TCP-разрешения
в WireGuard workers. Координатору не нужны TUN или root.

## Первый запуск

### Запуск без параметров

```sh
cargo build -p portal-runtime
sudo target/debug/portal-runtime
```

`portal-runtime run` без флагов делает то же самое. Если существует
`/etc/portal/runtime.json`, агент читает его для управляемого запуска.
Если файла нет, используются значения ручного режима:

| Параметр | По умолчанию |
|---|---|
| TUN-интерфейс | `portal0` |
| Приватный ключ | `/etc/portal/device.key` |
| UDP-сокет WireGuard | `0.0.0.0:51820` |
| Веб-панель и HTTP API | `127.0.0.1:51821` |
| Токен локального API | `/run/portal.token` |
| Адреса TUN | Пустой список; задаются через `--address` |
| MTU | `1420` |
| Workers | Число доступных CPU, максимум `256`; при ошибке определения — `4` |
| Порог рукопожатий | `100` в секунду до запроса cookie |
| Dual stack | Включён |
| Автоматические маршруты | Включены |

На первом ручном запуске отсутствующий ключ создаётся случайным и сохраняется
с правами `0600`; новые каталоги ключа создаются с правами `0700`. При рестарте
ключ остаётся прежним. Существующий повреждённый файл не перезаписывается.
В управляемом режиме отсутствующий ключ требует восстановления или явного
создания новой идентичности через `keygen`/`enroll`.

Откройте `http://127.0.0.1:51821/` и войдите токеном из `/run/portal.token`.
Чтобы изменить параметр ручного запуска, достаточно указать его одного:

```sh
sudo target/debug/portal-runtime run --tun test0 --listen 0.0.0.0:51900
```

Явные флаги ручного режима выбирают ручной запуск; автоматическое чтение
`/etc/portal/runtime.json` при этом не выполняется. `--config PATH` выбирает
управляемый режим и не совмещается с ручными флагами. Ошибка существующего
конфига не приводит к переключению в ручной режим.

### Подключение к координатору

Соберите workspace и запустите [координатор](COORDINATOR.md). Для runtime нужны
Linux, `iproute2` и права на создание TUN и настройку сети. Ниже агент работает
от root; его файлы состояния также должны принадлежать root.

```sh
cargo build --workspace
sudo install -d -m 700 runtime-state
sudo target/debug/portal-runtime keygen --private-key-file runtime-state/device.key
printf '{}\n' | sudo tee runtime-state/policy.json >/dev/null
sudo chmod 600 runtime-state/policy.json
sudo install -m 600 /path/to/user.token runtime-state/user.token
```

Токен пользователя выдаётся при регистрации на координаторе. Для учётной записи
`admin` он находится в `STATE_DIR/admin.token`. Он нужен только для регистрации
устройства: не сохраняйте его в конфигурации агента.

Отредактируйте [runtime/example.json](../runtime/example.json):

- `coordinator.url` — доступный устройству HTTPS origin без пути, query и пароля;
- `device_name` — имя устройства;
- `endpoints` — доступные другим пирам внешние UDP-адреса **этого** устройства;
  адрес `192.0.2.10` в примере замените своим;
- `ca_file` — доверенный сертификат/CA для разработки или частного центра
  сертификации. При отсутствии поля используются системные корни доверия;
- пути к ключу, credentials, политике, сохранённой карте и токену локального API.
  Относительные пути разрешаются от каталога JSON-конфига.

Все поля JSON можно опускать: верхний уровень получает те же значения
интерфейса, ключа, MTU, API и флагов, что приведены выше. Для секции
`coordinator` используются:

| Поле | По умолчанию |
|---|---|
| `url` | `https://localhost:8443` |
| `device_name` | `my-device` |
| `credential_file` | `/etc/portal/device.json` |
| `policy_file` | `/etc/portal/policy.json` |
| `map_file` | `/etc/portal/network-map.json` |
| `ca_file` | Не задан, используются системные корни доверия |
| `endpoints` | Пустой список |

Даже `{}` является конфигом управляемого режима с этими значениями. Для работы
нужны доступный координатор, его TLS-доверие и настоящие credentials устройства;
регистрация остаётся отдельным действием. У `enroll` значения флагов по умолчанию:
`--config /etc/portal/runtime.json` и `--user-token-file /etc/portal/user.token`.
При первой регистрации отсутствующий ключ создаётся автоматически. Повторная
регистрация не заменяет существующие credentials или потерянный ключ устройства.
`keygen` без флагов создаёт `/etc/portal/device.key` и отказывается перезаписывать
существующий файл.

`listen` задаёт локальный UDP-сокет. Внешние кандидаты пока указываются явно:
STUN, автоматический поиск LAN-адресов и port mapping ещё не реализованы.
Массив может быть пустым, но координатор отклоняет P2P-согласование без кандидатов.
Пока выбирается первый кандидат подходящего семейства; автоматического перебора
и проверки нескольких путей нет. Для первого соединения используйте достижимые
адреса LAN или явно открытый UDP-порт.

```sh
sudo target/debug/portal-runtime enroll \
  --config runtime/example.json --user-token-file runtime-state/user.token
sudo target/debug/portal-runtime run --config runtime/example.json
```

`enroll` отправляет публичный WireGuard-ключ токеном владельца и сохраняет
отдельные credentials устройства в `credential_file`. Приватный ключ остаётся
локально. Существующий файл не перезаписывается; обычный рестарт не регистрирует
устройство заново. При потере credentials владелец может отозвать устройство
или заменить его токен через API координатора. Ошибка сохранения после успешной
регистрации также требует такого восстановления через API.

Каталоги состояния должны иметь права `0700`, credentials, политика и карта —
`0600`, все от имени пользователя, запускающего агент. Карта сохраняется атомарно;
symlink вместо приватного файла отклоняется. Lock запрещает два процесса с одним
файлом credentials. После регистрации копия пользовательского токена агенту не нужна.

## Разрешения на устройстве

По умолчанию `policy.json` содержит `{}`. Чтобы разрешить конкретному устройству
TCP/8080 на этом устройстве назначения, запишите:

```json
{
  "ПУБЛИЧНЫЙ_WG_КЛЮЧ_ИСТОЧНИКА_64_HEX": { "tcp": [8080] }
}
```

Используйте настоящий ключ зарегистрированного устройства, например выведенный
его `keygen`. Право направлено: оно не открывает обратное подключение и другие
устройства владельца. Ответы разрешённого TCP-соединения проходят после
наблюдения SYN → SYN/ACK → ACK, отдельное обратное правило для них не нужно.

Агент перечитывает файл раз в секунду. Заменяйте файл целиком атомарным rename,
сохраняя владельца и права. Сначала применяются локальные ограничения, затем
агент публикует политику с ревизией. Новое разрешение начинает работать после
подтверждения активной привязки пира в карте координатора. Локальный отзыв
закрывает соответствующие потоки и при недоступном координаторе. Ошибка чтения
или формата политики блокирует трафик и останавливает агент.

При изменениях workers и применение карты используют общий gate. Агент очищает
ожидающий plaintext в BoringTun до включения новых правил, удаляет отозванных
пиров и инвалидирует больше не разрешённые TCP-потоки. Подходящие действующие
WireGuard-сессии и потоки сохраняются; обычное продление lease их не сбрасывает.
Ошибка применения карты закрывает доступ и запускает очистку ресурсов агента.
Установленные другими процессами маршруты агент не удаляет.

Ограничения первой версии: только TCP, без IPv4 options, фрагментов, IPv6 extension
headers и TCP Fast Open. UDP и ICMP через управляемый туннель блокируются.
Проверяются ключ, адрес источника, адрес назначения и разрешение потока;
одного флага ACK недостаточно. Это ACL, а полную проверку TCP выполняет стек ОС.
Таблица ограничена 8192 потоками на устройство: установление — 30 секунд,
простой — 300 секунд, закрытие после FIN — до 30 секунд. Для длительно
бездействующих соединений приложению нужен TCP keepalive с интервалом меньше
300 секунд. Exit node ещё не реализован.

## P2P-запрос и диагностика

### Локальная веб-панель

После запуска агента откройте `http://127.0.0.1:51821/` или адрес из
`api_listen`. Панель встроена в бинарник runtime; отдельный веб-сервер,
Node.js и установка фронтенд-зависимостей для запуска не нужны.

При запуске runtime сразу печатает строку `web panel: http://…/#token=…`
с готовой ссылкой для входа. Адрес и токен соответствуют текущему запуску;
при `api_listen` с портом `0` выводится фактически выбранный порт.

Чтобы получить готовую ссылку для входа без ручного копирования токена:

```sh
sudo target/debug/portal web
# Для нестандартного адреса или пути:
sudo target/debug/portal web --api 127.0.0.1:51821 --token-file runtime-state/api.token
```

Откройте выведенную ссылку в браузере. Команда только печатает ссылку и не
запускает браузер от root. Токен передаётся во фрагменте `#token=…`, который
браузер не отправляет HTTP-серверу. Панель сразу удаляет фрагмент из текущей
записи истории через `history.replaceState` и выполняет вход. Ссылка даёт доступ
к управлению локальным агентом — не передавайте её другим.

Также можно вставить токен из `api_token_file` или выбрать этот файл в форме входа.
Для стандартного ручного запуска токен находится в `/run/portal.token`,
для [примера управляемого запуска](../runtime/example.json) — в
`runtime-state/api.token`.

Панель показывает локальные адреса и ключ устройства, состояние координатора,
оставшееся время карты, пиров, действующие TCP-разрешения и статистику.
Есть поиск и кнопка P2P-запроса к пирам с разрешённым исходящим доступом.
Данные обновляются каждые пять секунд. Подтверждение запроса означает
согласование адресов; работающий прямой путь этим не подтверждается.
Разрешения пока редактируются в локальном файле политики.

Фронтенд обращается только к локальному HTTP API с того же origin:
`GET /api/v1/snapshot` возвращает структурированное состояние, а
`POST /api/v1/command` выполняет P2P-запрос через `operation: "connect"`.
Оба маршрута требуют bearer-токен. Снимок не содержит приватных ключей,
credentials координатора и путей к секретным файлам. Статические HTML/CSS/JS
доступны без токена; Host/Origin и loopback проверяются для всех маршрутов.

Токен сохраняется в `sessionStorage` этой вкладки; API-запросы передают его только
в заголовке `Authorization`, без query-параметров и cookies.
После обновления страницы панель автоматически проверяет сохранённый
токен и восстанавливает вход. Временная недоступность агента не удаляет токен:
можно повторить подключение без повторного ввода. Выход или ответ API `401`
очищает сохранённый токен и возвращает форму входа. После перезапуска агента
нужен новый токен из его файла.

### CLI

```sh
sudo target/debug/portal status --token-file runtime-state/api.token
sudo target/debug/portal list --token-file runtime-state/api.token
sudo target/debug/portal connect --device-id DEVICE_ID --token-file runtime-state/api.token
```

Локальный HTTP API принимает `{"operation":"connect","peer_device_id":"DEVICE_ID"}`.
A отправляет намерение координатору; агент B получает его через отдельный HTTPS
long poll, проверяет применённую карту и локальную политику, устанавливает endpoint
и отвечает. После ACK агент A проверяет данные B и устанавливает свой endpoint.
Сообщение `signaling=accepted path=unverified` подтверждает только согласование.
Hole punching, проверка достижимости, реле и состояния `direct/relayed` ещё не
реализованы. Карта уже содержит кандидаты: при прямой доступности WireGuard
может установить сессию и без отдельной команды `connect`.

`status` показывает ID устройства/сети, поколение и ревизию карты, ревизию
подтверждённой политики, `policy_pending`, состояние координатора и остаток lease.
При отклонённой публикации локальные ограничения продолжают действовать,
подтверждённая карта обновляется; причина HTTP-ошибки видна в stderr.
Ручные `peer upsert/remove` и `endpoint set/clear` в управляемом режиме запрещены.
Разрешения меняются через локальный файл.

При обрыве HTTPS агент повторяет запросы; действующая карта работает до своего
срока. Проверка срока монотонная и выполняется на пути пакета, включая выдачу
очереди. По истечении срока трафик блокируется; свежая карта восстанавливает
доступ. После сетевой ошибки агент запрашивает карту сразу без ожидания изменений.
Отозванный токен закрывает доступ и завершает процесс.

Сохранённая карта фиксирует идентичность сети, адреса и курсор. На старте
требуется свежий HTTPS-ответ: офлайн-запуск из кеша пока не поддерживается.
Проверяются версия протокола, ключ/владелец/ID устройства, дубли IP и ключей,
возврат ревизии назад и сроки. Подмена идентичности не применяется.

Ручной режим с `run --tun ... --address ...` сохраняется для разработки и
совместимости с обычным WireGuard. В нём разрешения координатора не действуют.

## Проверки

```sh
cargo test --workspace --offline
cargo build --workspace --offline
unshare --user --map-root-user --net python3 runtime/scripts/check-managed.py
unshare --user --map-root-user --net --mount python3 runtime/scripts/check-defaults.py
```

Проверка `check-managed.py` требует разрешённых user namespaces, `ip`, `nsenter`,
`openssl` и Python 3. Создаются два изолированных network namespace, HTTPS-координатор,
два агента и TCP-сервер. Проверяются IPv4/IPv6, согласование, запрет другого порта,
офлайн-отзыв действующего TCP-потока, истечение lease, переподключение и отзыв
устройства. Сетевые настройки хоста не меняются. Обычные unit-тесты также
проверяют очистку очереди перед handshake и сохранение действующей WG-сессии.

`check-defaults.py` также требует `mount` и монтирует временные `/etc` и `/run` только
внутри namespace и проверяет запуск без аргументов, постоянство ключа,
автоматический выбор конфига и явные переопределения параметров.
