# UDP-пир-реле

Обычный Portal-пир может пересылать зашифрованные пакеты других участников.
Пересылка находится в `net/src/peer_relay.rs`, работает на существующем Tokio
runtime и использует дополнительный UDP-порт. HTTPS-сервера, домена, файлов
сертификатов и внешнего `iroh-relay` больше нет.

## Настройка реле

Шаблон: [deploy/portal-relay.json.example](../deploy/portal-relay.json.example).
Замените `PUBLIC_IP` и ключи клиентов настоящими значениями. `device.key`
остаётся обычным Ed25519-ключом устройства, пути разрешаются рядом с JSON.

```json
"relay_server": {
  "listen": "0.0.0.0:40000",
  "public_endpoint": "PUBLIC_IP:40000",
  "allowed_peers": ["PUBLIC_KEY_OF_A_HEX", "PUBLIC_KEY_OF_B_HEX"]
}
```

`public_endpoint` должен содержать глобально маршрутизируемый IP. Частные,
CGNAT, link-local и документационные диапазоны отклоняются. Для локальной
проверки разрешён одинаковый loopback-адрес в обоих полях, например
`127.0.0.1:40000`. Проверка адреса не доказывает владение IP или доступность
извне: объявленный UDP-порт должен вести на это устройство.

`listen` верхнего уровня — отдельный UDP endpoint обычных сервисов. Его можно
оставить `null`: тогда собственные сервисы реле доступны через транспорт
пересылки. Root и системные виртуальные интерфейсы не требуются.

## Настройка клиентов

На A и B задайте общий пир-реле:

```json
"relays": [
  {"public_key": "RELAY_PUBLIC_KEY_HEX", "endpoint": "PUBLIC_IP:40000"}
]
```

Оба клиента должны быть разрешены на реле. Зарегистрируйте ключи A и B друг у
друга для обычного QUIC-соединения; доступ к файлам отдельно разрешите на B.
Регистрировать R как обычного доверенного пира для использования пересылки
необязательно. Для чтения собственных файлов R нужно обычное взаимное доверие.

`listen: null` у клиента отключает прямой IP-транспорт приложения. UDP для
исходящего соединения с реле всё равно используется. При полностью заблокированном
UDP этот транспорт не работает; запасного HTTPS-реле сейчас нет.

Для отдельного маршрута к одному устройству `peer_upsert` принимает:

```json
{
  "operation": "peer_upsert",
  "public_key": "TARGET_PUBLIC_KEY_HEX",
  "endpoint": null,
  "relay": {"public_key": "RELAY_PUBLIC_KEY_HEX", "endpoint": "PUBLIC_IP:40000"}
}
```

CLI: `portal peer upsert --public-key TARGET_KEY --relay-key RELAY_KEY
--relay-endpoint PUBLIC_IP:40000` с обычными `--api` и `--token-file`.
В интерфейсе используются два поля: ключ и UDP-адрес пира-реле. Идентичность
реле проверяется по этому ключу самим iroh; обычный публичный TLS-сертификат
не требуется. Конечное устройство также проходит отдельную проверку ключа.

## Как передаются данные

```text
        зашифрованное внутреннее QUIC-соединение A ↔ B
A ── QUIC DATAGRAM / UDP ── R ── QUIC DATAGRAM / UDP ── B
```

У каждого участника есть endpoint приложения и endpoint транспорта пересылки.
R принимает аутентифицированные подключения `portal-peer-relay/1`. После допуска
клиент проходит короткую регистрацию и поддерживает соединение keepalive.
Разрешённый клиент отправляет ключ назначения и непрозрачные фрагменты пакета.
R подставляет подтверждённый ключ отправителя и пересылает их подключённому
адресату. У R нет ключей внутреннего QUIC-соединения A ↔ B.

Прямые UDP-адреса и relay-адреса представлены iroh как разные пути. Выбор пути
предпочитает работающий прямой UDP. Iroh использует известные адреса и обмен
адресами между пирами, но отдельного публичного STUN/координатора в этой версии
нет: автоматическое обнаружение внешнего адреса за произвольным NAT не гарантируется.
Достижимое реле обеспечивает связь через исходящий UDP при отсутствии прямого пути.

Custom transport принимает и отправляет ненадёжные DATAGRAM, поэтому потерянные
пакеты восстанавливает внутренний QUIC. Надёжные потоки между A и R для пересылки
не используются. Это сохраняет независимость файловых потоков при потерях.
Внешние QUIC-соединения также имеют собственное шифрование и congestion control;
это не реализация совместимого с Tailscale wire-протокола.

Для MTU используются фрагменты до 1000 байт полезной нагрузки; внутренний пакет
ограничен 2048 байтами. На один relay-клиент приходится очередь 256 пакетов,
до 64 незавершённых сборок с TTL 2 секунды. Реле допускает до 128 подключённых
клиентов, клиент — до 16 адресов реле. Переполнение приводит к потере датаграмм,
а не к неограниченному росту памяти. Повторное подключение к реле выполняется
автоматически. Iroh зафиксирован на 1.4.0, поскольку custom transport API нестабилен.

## Разрешения и жизненный цикл

`relay_server.allowed_peers` отделён от реестра доверенных пиров и
`files.allowed_downloaders`. Пустой список не открывает доступ посторонним.
Отзыв разрешения удаляет зарегистрированное подключение и закрывает его;
каждая пересылка дополнительно проверяет разрешения отправителя и адресата.
Удаление Portal-пира также отзывает его доступ к своему relay.

В разделе «Система» видны UDP-адрес реле, клиенты и список разрешённых ключей.
В форме устройства можно изменить «Разрешить использовать моё реле».
Для управления отдельным ключом:

```json
{"operation":"relay_access_set","public_key":"PEER_KEY_HEX","allowed":false}
```

Запрос отправляется в локальный `POST /api/v1/command` с bearer-токеном.
Изменения через API действуют до рестарта; постоянные разрешения хранятся в
конфигурации. `services_reload` перезапускает только прикладные сервисы,
а relay-соединения и их живые разрешения сохраняются.

Служебная операция `portal/info` возвращает ключ устройства и необязательный
объект `relay_server` с ключом и UDP-адресом. Локальный маршрут
`POST /api/v1/peers/info` принимает `{"peer":"PEER_KEY_HEX"}`, проверяет ответ
и сохраняет роль для интерфейса. Объявление роли само по себе не подключает
клиента к неизвестному реле: выбор остаётся явным.

## Проверка

```sh
cargo test -p portal-net --test relay -- --include-ignored
cargo build -p portal-runtime -p portal-cli
python3 runtime/scripts/check-peer-relay.py
```

Четыре runtime проверяют A → R → B, чтение собственных файлов R, объявление
роли, независимые разрешения, отказ постороннему ключу, живой отзыв/возврат доступа,
перезагрузку сервисов и освобождение UDP-порта при остановке. Отдельный тест
проверяет приоритет прямого пути и его работу после отзыва relay-доступа.

## Миграция

Прежние URL в `relays` и `peer_upsert.relay` замените объектами с ключом и
UDP-адресом. В `relay_server` удалите `public_url`, `tls` и `quic_listen`, задайте
`listen` и `public_endpoint`. Обычные ключи устройств и права файлов сохраняются.
