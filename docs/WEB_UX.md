# UX веб-панели Portal

Статус: целевой UX и состояние реализации на 2026-11-05.
Подключение одной сети, реестр аккаунта и политики реализованы; оставшиеся
границы перечислены в разделе 11.
Текущую реализацию описывают [RUNTIME.md](RUNTIME.md) и
[COORDINATOR.md](COORDINATOR.md); устройство транспорта —
[NETWORK_PLAN.md](NETWORK_PLAN.md).

## 1. Цель и принятые решения

Пользователь подключается к сети, добавляет устройства, управляет разрешениями
и устанавливает соединения через веб-панель. Для обычной работы не нужны CLI,
ручное редактирование JSON, чтение файлов через `sudo` и перенос секретов между
файлами. Установка и запуск локального приложения остаются задачей ОС/установщика;
браузер сам не создаёт TUN и не получает системные привилегии.

Приняты следующие решения:

- Клиент распространяется одним бинарником `portal`, объединяющим агент,
  локальный HTTP API, веб-панель и необязательный CLI. Координатор — отдельный сервер.
- Первый экран предлагает вход или регистрацию на выбранном координаторе.
- Вход выполняется по адресу координатора и токену пользователя.
- Регистрация запрашивает имя пользователя и создаёт учётную запись и первое устройство.
- Пока клиент работает с одной сетью. Несколько сетей и переключение профилей отложены.
- Имя устройства назначает агент (`device-…`); его можно изменить перед добавлением
  и затем в параметрах собственного устройства. Для следующего своего
  устройства пользователь использует вход с уже выданным токеном.
- Приватный WireGuard-ключ создаёт и хранит локальный агент. Публичный ключ
  подставляется в форму автоматически, пользователь не вычисляет его вручную.
- Авторизация остаётся на токенах. Отдельную пару ключей Ed25519 не вводим.
- Панель показывает все собственные устройства, включая недоступные, и карту
  разрешённых связей. Право видеть устройство не даёт права передавать ему трафик.
- Владелец управляет разрешениями каждого своего устройства через панель.
- P2P-запрос выполняется от текущего устройства. При действующем разрешении
  целевой агент отвечает автоматически, без подтверждения человеком.
- Принадлежность устройств одному владельцу сама по себе не открывает доступ.
- Архитектура управления должна допускать будущую веб-панель без локального
  агента. Функции управления аккаунтом не должны зависеть от WireGuard-ключа.

## 2. Сущности и области действия

| Сущность | Назначение |
|---|---|
| Координатор | HTTPS-сервер регистрации, реестра устройств, разрешений и P2P-согласования |
| Сеть | Сеть с устойчивым ID, обслуживаемая координатором |
| Пользователь | Учётная запись на конкретном координаторе, владелец устройств |
| Текущее устройство | Устройство, на котором работает локальный агент, обслуживающий эту панель |
| Собственное устройство | Устройство выбранной сети, принадлежащее вошедшему пользователю |
| Чужое доступное устройство | Устройство другого пользователя, разрешённые связи с которым видны вошедшему пользователю |
| Профиль сети | Сохранённые параметры подключения и credentials конкретной сети |
| Политика устройства | Разрешения на входящие подключения к портам именно этого устройства |

Учётные записи и права независимы между координаторами. Вход в одну сеть
не авторизует пользователя в другой. Идентификаторы устройств рассматриваются
в контексте сети; совпадение имени не означает совпадение устройства.

Владелец координатора — `admin`. Создание сети начинается с запуска координатора,
который создаёт сеть и учётную запись `admin`. Это не даёт admin автоматического
доступа к чужим устройствам и управления их политиками.

### 2.1. Три разных вида токенов

| Токен | Кому и для чего нужен | Где используется |
|---|---|---|
| Пользователя | Вход в аккаунт, список собственных устройств, добавление устройств, изменение их разрешений | API управления аккаунтом на выбранном координаторе |
| Устройства | Фоновая работа конкретного агента: карта, endpoints, P2P, отчёт о применении настроек | API устройства на координаторе |
| Локального API | Защита управления локальным агентом из браузера | Только локальный HTTP API |

Токен устройства не позволяет управлять всеми устройствами владельца.
Токен локального API не является токеном входа в сеть и не отправляется
координатору. Токен пользователя не передаётся другим пирам.

Для целевого UX пользовательский токен нужен не только при добавлении устройства:
он используется для последующего управления всеми своими устройствами.
Это изменение относительно текущего сценария CLI-enrollment.

## 3. Первый запуск и доступ к панели

1. Пользователь запускает установленный клиент и открывает локальную веб-панель.
2. Клиент обеспечивает доступ браузера к локальному API без ручного чтения
   `/run/portal.token`. Уже существующая ссылка с `#token=…` может служить
   механизмом передачи локальной сессии при открытии панели.
3. После локальной авторизации, если профилей ещё нет, основной экран сразу
   показывает форму подключения к координатору.
4. Создание ключа, каталогов и файлов состояния выполняет агент. Пользователю
   не предлагаются пути к credentials, политике или приватному ключу.

Локальная авторизация и вход в сеть — разные этапы. Форма первого входа в сеть
не должна требовать от пользователя разобраться в этом разделении или вводить
токен локального API вместо токена аккаунта.

Если агент не установлен, не запущен или не получил системные права, панель
показывает понятное состояние и действие для запуска/восстановления клиента.
Способ открытия браузера и получения привилегий установщиком ещё предстоит
определить; он не должен становиться обязательной CLI-процедурой подключения
к каждой сети.

## 4. Экран подключения

Две вкладки или два явно различимых режима: **«Войти»** и **«Регистрация»**.
Переключение сохраняет введённый адрес координатора. Секретные поля не должны
попадать в URL, историю навигации или общий журнал приложения.

### 4.1. Вход

Основная форма содержит ровно два поля:

| Поле | Поведение |
|---|---|
| Адрес координатора | Домен или IP, при необходимости с портом; также допускается полный HTTPS origin |
| Токен входа | Скрытое поле для токена пользователя с возможностью показать/скрыть |

Кнопка: **«Войти в сеть»**. Ссылка рядом: **«Нет токена? Зарегистрироваться»**.
Токен устройства, токен локального API и произвольная строка должны приводить
к объяснению, какой токен нужен, без вывода введённого секрета в ошибку.

После нажатия:

1. Агент нормализует адрес и проверяет HTTPS-соединение и сертификат.
2. Координатор проверяет пользовательский токен и возвращает аккаунт и ID сети.
3. Панель получает полный список собственных устройств.
4. Агент сопоставляет свой публичный WireGuard-ключ с этим списком.
5. Если устройство уже принадлежит этому аккаунту, используется существующая
   запись. Не создаются дубликат, новый ключ или новое имя при каждом входе.
6. Если такого устройства нет, открывается короткий шаг **«Добавить это
   устройство»** с именем и автоматически подставленным публичным ключом.
   Имя можно предложить по имени компьютера, но пользователь может изменить его.
7. После успешного добавления агент получает собственный токен устройства,
   применяет сетевые настройки, сохраняет профиль и открывает основной экран.

Вход с пользовательским токеном не означает, что ранее выданный токен устройства
можно прочитать из координатора. Если локальная копия утрачена, нужен явный
процесс восстановления credentials; см. раздел 12.

### 4.2. Регистрация

Основная форма:

| Поле | Поведение |
|---|---|
| Адрес координатора | Такие же правила, как при входе |
| Имя пользователя | Обязательное уникальное имя аккаунта на этом координаторе |
| Имя устройства | Служебное имя назначает агент; доступно изменение на шаге добавления и в параметрах |
| Публичный ключ WireGuard | Подставлен агентом; доступен просмотр и копирование, ручной ввод для текущего устройства не требуется |

Кнопка: **«Зарегистрироваться и подключиться»**.

Публичный ключ показывается как идентификатор текущего устройства, а не как
секрет или пароль. Агент должен иметь соответствующий приватный ключ.
Ввод произвольного чужого публичного ключа не является способом начать работу
от имени того устройства. Предварительное добавление удалённого устройства —
возможное отдельное действие, не часть этой формы.

Регистрация выполняет последовательно:

1. Проверку доступности координатора и доверия TLS.
2. Создание учётной записи пользователя на этом координаторе.
3. Получение пользовательского токена и его надёжное локальное сохранение.
4. Добавление первого устройства к созданной учётной записи.
5. Сохранение credentials устройства, применение конфигурации и открытие сети.

В разделе «Сеть и аккаунт» доступны явные действия «Скопировать токен» и
«Сохранить токен в файл». Напоминание о сохранении токена не показывается. Секрет не показывается постоянно
в основном интерфейсе. Панель не запрашивает дополнительный CLI-вызов для
получения только что выданного токена.

Имя пользователя вводится явно и независимо от имени устройства. Совпадающие
имена устройств у разных пользователей допустимы. При конфликте имени аккаунта
пользователь исправляет поле; секрет и этап регистрации сохраняются агентом.

Сегодня регистрация открыта. Когда admin ограничит её, та же форма должна
показывать отказ, необходимость приглашения или ожидание одобрения, если такой
режим будет реализован. Нельзя изображать успешный вход до фактического допуска.

### 4.3. Адрес, HTTPS и доверие

- Для домена/IP без схемы используется HTTPS; итоговый адрес отображается
  пользователю. Адреса с явным нестандартным портом сохраняют этот порт.
- Явный HTTP не принимается и не служит автоматическим fallback.
- Пароль в URL, произвольный путь, query и fragment не являются частью адреса
  координатора. API работает с HTTPS origin.
- Для короткой формы без порта используется стандартный HTTPS-порт `443`.
  Нестандартный порт, включая `8443`, пользователь указывает явно.
- При неизвестном CA предусмотрен дополнительный шаг выбора доверенного
  сертификата/CA через браузер. Не требуется вводить путь к файлу на машине агента.
- Нельзя решать ошибку TLS переключателем «отключить проверку». Ошибки имени
  сервера, срока сертификата и недоверенного CA объясняются отдельно по возможности.

## 5. Повторный вход и одна сеть

В текущей версии агент сохраняет один профиль: origin координатора, ID сети,
аккаунт, пользовательский токен, credentials устройства и выбранный CA.
Профиль и credentials сохраняются агентом с правами `0600`, каталог — `0700`.
Браузер хранит только локальную сессию; пользовательский токен в его хранилище
не попадает. Перезапуск агента восстанавливает подключение, обновление вкладки
восстанавливает локальную сессию.

Вход в другой origin отклоняется до отправки туда сохранённого секрета.
Смена ID сети при восстановлении блокирует применение сети. Одновременная
работа и переключение нескольких сетей отложены по согласованному решению.

Действия различаются:

| Действие | Результат |
|---|---|
| Закрыть/обновить вкладку | Не удаляет устройство и не отзывает разрешения |
| Выйти из панели | Завершает сессию браузера; фоновый VPN продолжает работать |
| Удалить устройство из сети | После явного подтверждения отзывает устройство на координаторе; старые карты ограничены lease |

Отдельные действия «Отключить сеть» и «Забыть профиль» пока не реализованы;
выход из панели не должен их имитировать. Для будущего нескольких сетей
потребуются изоляция credentials, явное переключение и правила конфликтов адресов.

## 6. Основной экран сети

После входа пользователь видит выбранную сеть и аккаунт, текущее устройство,
список своих устройств, карту разрешённых связей и состояние координатора.
Краткий список в обзоре включает текущее устройство, собственные устройства
из реестра и разрешённых пиров с устранением повторов по публичному ключу.
Отсутствие удалённых пиров не означает пустую сеть: текущее устройство остаётся
видно с отдельной отметкой, а счётчики обзора и списка используют один состав.
Для собственного устройства доступны просмотр, разрешения и удаление из сети.
Для текущего устройства дополнительно доступны действия подключения к пирам.

Нужны три независимых признака:

1. **Собственность:** моё / чужое; текущее устройство отмечено отдельно.
2. **Разрешения:** можно подключаться / только входящий доступ / доступа нет.
3. **Связность:** неизвестна / проверяется / прямой путь подтверждён / недоступно.

Не следует объединять их в один зелёный индикатор «подключено».
Наличие устройства в реестре, endpoints или действующего разрешения не доказывает
его доступность. Статус координатора также не доказывает исправность P2P-пути.

### 6.1. Список устройств

Все собственные неотозванные устройства видны даже при отсутствии разрешений
и при выключенном агенте. Отозванные устройства, если показываются, находятся
в отдельном состоянии и не выглядят доступными для подключения.

В строке/карточке устройства отображаются:

- Имя, отметки «Ваше» и «Это устройство».
- Виртуальные адреса и публичный ключ в подробностях, с копированием.
- Доступные направления TCP-доступа и порты назначения.
- Состояние присутствия агента, если для него есть надёжные данные.
- Состояние пути от текущего устройства и время последней проверки, если известно.
- Наличие неприменённых изменений разрешений.

Предусмотреть поиск по имени, адресу или публичному ключу. Для чужих устройств
отображаются только данные, разрешённые вошедшему пользователю. Нельзя выдавать
весь глобальный реестр координатора ради построения карты.

Присутствие агента и время последней активности должны иметь отдельный источник
данных на сервере. В текущем API такого полноценного статуса нет; нельзя
объявлять устройство онлайн только по факту его регистрации.

### 6.2. Карта сети

Карта показывает устройства и направленные разрешённые связи между ними.
Собственные устройства остаются на карте без рёбер. Дополнительно показываются
чужие устройства и связи, на просмотр которых у пользователя есть право.
Полный состав такой видимости задаётся сервером, а не фильтром браузера.

Пример: `Ноутбук → Сервер · TCP 443, 8080` означает разрешение ноутбуку обращаться
к этим портам сервера. Обратное направление требует отдельного разрешения.

Вид связи различается в легенде:

- Разрешение задано, но ещё не применено целевым устройством.
- Доступ разрешён и применён, но путь не проверен.
- Идёт согласование/проверка пути от текущего устройства.
- Прямой путь подтверждён текущим агентом.
- Путь потерян или последняя попытка завершилась ошибкой.

Карта разрешений — не снимок фактического прохождения пакетов через координатор:
полезный трафик идёт между пирами. Нельзя показывать связь двух удалённых
устройств как подтверждённую, если текущий агент знает только о разрешении.
Для таких рёбер нужна отдельная телеметрия либо честное состояние «не проверено».

Клик по узлу открывает устройство; клик по ребру — направление и порты.
Из карты можно перейти к редактированию разрешений собственного устройства.
Список устройств остаётся полноценной альтернативой графу на узком экране
и при работе с клавиатурой.

## 7. Управление разрешениями

### 7.1. Направление и представление

Разрешения хранятся отдельно для каждого целевого устройства:

```json
{
  "PUBLIC_WIREGUARD_KEY_OF_SOURCE": { "tcp": [443, 8080] }
}
```

В интерфейсе это редактор **«Кто может подключаться к этому устройству»**.
Пользователь выбирает устройство из списка по имени и адресу, без ввода ключа.
В списке объединены собственные устройства из реестра аккаунта, текущее устройство
и известные агенту чужие устройства; целевое устройство исключено, дубликаты удалены.
Запись по-прежнему привязывается к публичному ключу источника. Сохранённые разрешения
для источников, отсутствующих в доступном списке, сохраняются как «Недоступное устройство».

Типовые сервисы выбираются галочками: SSH (TCP 22), RDP (TCP 3389), VNC (TCP 5900),
HTTP (TCP 80), HTTPS (TCP 443), SMB (TCP 445). Остальные TCP-порты вводятся через
запятую в отдельном поле. При загрузке правила типовые порты отмечаются галочками,
остальные остаются в поле; при сохранении и массовом применении оба набора объединяются.
WireGuard — транспорт Portal, отдельное TCP-разрешение для включения туннеля не требуется.

Например, на сервере разрешение `Ноутбук коллеги: TCP 8080` даёт коллеге доступ
к порту 8080 сервера. Оно не распространяется на телефон владельца, не открывает
обратное направление и не предоставляет все порты сервера.

- Владелец может изменять политики любого своего устройства, включая удалённое.
- Чужие политики доступны только для просмотра разрешённой части; изменить их
  нельзя, даже подставив ID чужого устройства в HTTP-запрос.
- Право управлять своим устройством не означает автоматического сетевого доступа.
- Владелец координатора не получает специального доступа к чужим политикам.
- Для первой реализации редактируются TCP-порты. UDP и диапазоны портов
  нельзя обещать, пока не определена и не реализована соответствующая модель.
- Пустой список/удаление записи означает отсутствие предоставленного доступа.

Должен существовать способ выбрать зарегистрированное устройство, ещё не
попавшее в карту разрешённых пиров, иначе первое разрешение невозможно выдать.
Для чужого источника можно предусмотреть поиск или добавление по публичному
ключу; объём раскрываемых при поиске данных требует отдельного решения.

### 7.2. Сохранение и применение

Координатор хранит желаемую политику владельца. Целевой агент получает её,
применяет на пути пакетов и подтверждает конкретную ревизию. Устаревший локальный
файл не должен перезаписывать новое изменение из веб-панели.

Видимые состояния:

| Состояние | Значение |
|---|---|
| Есть несохранённые изменения | Редактирование существует только в форме |
| Сохраняем | Запрос к координатору ещё не завершён |
| Сохранено, ожидает устройства | Координатор принял желаемую ревизию, но агент её не подтвердил |
| Применено | Целевой агент подтвердил применение этой ревизии |
| Ошибка применения | Изменение сохранено, но агент сообщил об ошибке |
| Конфликт изменений | Другой клиент изменил политику; требуется загрузить актуальную ревизию |

Выключенное устройство не препятствует сохранению желаемой политики, но панель
не показывает её как применённую. После возвращения агент получает актуальную
ревизию. Подтверждение старой ревизии не подтверждает более новую.

Редактор использует контроль ревизий, чтобы два окна не перезаписывали изменения
друг друга незаметно. При конфликте введённые пользователем данные сохраняются
для сравнения/повторного редактирования, а не исчезают.

Выдача нового разрешения не должна открывать доступ до его реального применения.
При отзыве следует закрыть больше не разрешённые потоки и очереди согласно
сетевой модели. Если устройство недоступно, немедленное применение отзыва
обещать нельзя: старые разрешения ограничены сроком действия ранее выданной
карты. Интерфейс показывает ожидание и известные сроки, а не сообщение
«доступ закрыт везде» по одному ответу координатора.

### 7.3. Распространение на свои устройства

Дополнительное действие: **«Применить это разрешение ко всем моим устройствам»**.
Оно не включено по умолчанию и требует отдельного осознанного выбора.

Перед применением показываются источник, порты и список целевых собственных
устройств. Операция создаёт отдельные изменения политик этих устройств,
а не глобальное разрешение аккаунта. Целевое устройство, совпадающее с источником,
исключается; выдача доступа самому себе не требуется.

Результат отображается по каждому устройству: сохранено, ожидает, применено,
конфликт или ошибка. Частичный успех не выдаётся за полный. Такое распространение
не означает автоматическое наследование разрешения будущими устройствами.

## 8. Подключение к пиру

Пользователь выбирает устройство и нажимает **«Подключиться с этого устройства»**.
Текущее устройство явно указано. Выбор другой карточки не превращает её
в источник подключения: удалённое управление установлением соединений между
двумя другими устройствами в этот сценарий не входит.

Кнопка учитывает исходящее разрешение текущего устройства на порты назначения
целевого. Входящее разрешение в обратную сторону не делает кнопку доступной.
При отсутствии права панель объясняет причину и, если пользователь владеет
целевым устройством, предлагает открыть его редактор разрешений.

Последовательность:

1. Текущий агент A отправляет намерение подключиться к B координатору.
2. Координатор проверяет актуальные права и доставляет запрос агенту B.
3. Агент B автоматически проверяет свою применённую политику и отвечает.
4. A и B получают/уточняют адреса и ключи, выполняют hole punching и проверку пути.
5. Панель показывает подтверждённое прямое соединение только после проверки
   транспортом, а не сразу после ответа координатора.

Подтверждения человеком у B нет. Получение P2P-запроса не выдаёт новое разрешение.
Действующий доступ всё равно проверяется на конечных устройствах при передаче
трафика. Отзыв во время установления соединения должен прекращать попытку.

Состояния попытки: «Запрос отправляется», «Ожидаем ответ устройства»,
«Проверяем прямой путь», «Прямое соединение установлено» либо конкретная ошибка.
Повторный клик не создаёт параллельные одинаковые запросы.

Сеть может автоматически поддерживать доступные прямые пути и без ручного клика.
Кнопка инициирует/ускоряет попытку, а не является способом открыть TCP-порт
или автоматически запустить файловый сервис.

Релейный fallback — будущий этап. Пока он отсутствует, невозможность построить
прямой путь показывается как ограничение/ошибка, без вымышленного статуса «через реле».

## 9. Ошибки и незавершённые операции

| Ситуация | Ожидаемое поведение |
|---|---|
| Неверный адрес | Ошибка возле поля, введённые данные сохраняются |
| Координатор недоступен | Возможность повторить; существующие профили не удаляются |
| Сертификат не принят | Пояснение и настройка доверенного CA через панель |
| Неверный/отозванный пользовательский токен | Запрос нового токена для этого профиля, без удаления других сетей |
| Отозван токен устройства | Управление аккаунтом и список устройств могут оставаться доступны; агент показывает необходимость восстановления доступа устройства |
| Регистрация закрыта | Явное сообщение о недоступности регистрации |
| Ключ принадлежит другому аккаунту | Отказ, без присвоения записи и без автоматической смены ключа |
| Аккаунт создан, устройство добавить не удалось | Сохранить уже выданный токен; предложить продолжить добавление, не создавать новый аккаунт |
| Устройство добавлено, ответ потерян | Сначала проверить реестр собственных устройств; не повторять регистрацию вслепую |
| Повторное нажатие/обновление страницы | Восстановить известный этап; не плодить аккаунты и устройства |
| Агент не смог применить сеть | Показать ошибку, сохранить успешную регистрацию для повторной попытки |
| Координатор недоступен после входа | Последние данные с отметкой устаревания; без ложного подтверждения сохранения изменений |
| Карта просрочена | Агент закрывает доступ согласно модели lease, панель показывает причину |
| Пир не ответил/P2P не удался | Ошибка конкретной попытки, возможность повторить без повторного входа |
| Локальный агент недоступен | Состояние потери связи с клиентом, отличимое от ошибки координатора |

Сетевой timeout не доказывает, что сервер не выполнил операцию. Регистрация
и добавление устройства требуют стратегии повторов/идемпотентности. Её нельзя
заменять повторной отправкой создания аккаунта после каждого timeout.

Обновление данных в фоне не сбрасывает открытый редактор и несохранённые поля.
Кнопки отражают выполняемую операцию; ошибки показываются рядом с ней, а не
только кратковременным toast. Пользователю не выводятся трассировки и секреты.

## 10. Хранение и будущая панель без клиента

В локальном варианте браузер обращается к локальному API, а агент — к координатору
по проверенному HTTPS. Локальный API проверяет авторизацию и допустимый origin;
наличие пользовательского токена не отменяет защиту локального агента.

Приватный WireGuard-ключ и токены устройств не возвращаются в обычных снимках
состояния и не передаются пирам. Секреты профилей сохраняются агентом с правами
владельца; токен пользователя показывается/экспортируется только по отдельному
действию. Ошибки, логи и телеметрия не содержат токенов и приватных ключей.

Будущая веб-панель без установленного клиента сможет:

- Входить по пользовательскому токену на выбранный координатор.
- Показывать собственные устройства и разрешённую пользователю карту связей.
- Управлять разрешениями и регистрационными записями собственных устройств.

Она не сможет изображать «текущее WireGuard-устройство» браузера или выполнять
P2P через TUN без соответствующего агента. Кнопка подключения от локального
устройства доступна только при наличии работающего агента и его идентичности.

Для такой панели нужно отдельно определить размещение, сессии и правила
междоменного доступа. Не следует заранее открывать произвольный CORS или
отдавать браузеру токены всех устройств только ради будущей совместимости.

## 11. Состояние реализации

| Область | Реализовано |
|---|---|
| Подключение | Вход с origin и пользовательским токеном, регистрация с именем аккаунта, автоматически созданный ключ и редактируемое служебное имя устройства |
| TLS | HTTPS по умолчанию на 443, запрет HTTP/путей/credentials в URL, выбор PEM CA через браузер без отключения TLS |
| Credentials | Один профиль, сохранение агентом, экспорт пользовательского токена по отдельному действию, восстановление при запуске |
| Повторы | Секреты регистрации/enrollment генерируются агентом и сохраняются до запроса; сервер хранит хеши, повтор возвращает ту же идентичность |
| Реестр | Все собственные неотозванные устройства из API аккаунта, включая устройства вне карты; чужие — только из разрешённой карты агента |
| Управление | Переименование, отзыв устройства, входящие TCP-разрешения любого своего устройства; проверка владельца на сервере |
| Политики | Желаемая ревизия и подтверждённая агентом ревизия, конфликт `409`, сохранение черновика, блокировка старого файлового publisher после перехода на управление владельцем |
| Карта | Доступное с клавиатуры представление направленных связей текущего устройства с портами; текущее и собственные изолированные устройства сохраняются; переход к параметрам, легенда и известные ревизии политик |
| Массовые разрешения | Предварительный список своих целей без источника, явное подтверждение, отдельные записи с контролем ревизий и сохранением других источников, частичные результаты и подтверждения устройств |
| Защита сессии | Напоминание об экспорте токена, копирование публичных ключей и адресов; очистка форм и результатов при выходе; перенаправленный журнал агента содержит адрес панели без локального токена |
| P2P | Запрос от текущего агента, автоматический ответ по действующим правам, подтверждение прямого пути, ошибки конкретной попытки |

Остаются отдельными задачами: интеграция открытия локальной панели с установщиком
без CLI, полная карта аккаунта со связями между удалёнными узлами, heartbeat
присутствия, восстановление утраченных credentials, отдельное отключение/удаление
профиля и подробные промежуточные стадии P2P.
Системные ошибки подключения и TLS различаются лишь в пределах информации
HTTPS-клиента; неизвестный статус не выдаётся за онлайн или установленный путь.

Текущие endpoint, хранение и миграция описаны в [RUNTIME.md](RUNTIME.md) и
[COORDINATOR.md](COORDINATOR.md). Браузерные проверки включают конфликты и частичный успех массовой выдачи прав,
подтверждение конкретной ревизии и сохранение черновика; используют контролируемый локальный API; HTTPS также
проверяется отдельно без TUN. Скрипты `check-web-network.py`, `check-defaults.py`
и `check-managed.py` дополнительно проверяют настоящий TUN в изолированных
user/mount/network namespaces, не меняя сеть и системные файлы хоста.

## 12. Открытые вопросы перед реализацией

1. **Имя аккаунта — решено.** Пользователь вводит имя аккаунта. Имя устройства
   служебное, назначается агентом и может быть изменено.
2. **Утраченные device credentials.** Как подтверждать восстановление существующего
   устройства с тем же публичным ключом и не отзывать незаметно другой живой агент?
   Существующая операция ротации токена от пользователя отзовёт прежний токен;
   её нельзя выполнять автоматически при каждом входе.
3. **Утраченный токен пользователя.** Координатор хранит хеш, а не исходный токен.
   Повторная выдача, восстановление аккаунта, ротация и полномочия восстановления
   требуют отдельного решения. Пока допустим экспорт при наличии локальной копии,
   но нельзя обещать восстановление по имени устройства или публичному ключу.
4. **Несколько сетей — отложено.** Пока поддерживается одна сеть.
5. **Источник первого разрешения — реализовано.** Выбор собственного устройства
   или известного пира; для другого устройства вводится публичный ключ. Глобальный
   реестр не раскрывается.
6. **Карта аккаунта.** Определить разрешённую видимость чужих узлов/рёбер и источник
   сведений о соединениях между двумя удалёнными устройствами.
7. **Доставка политик — реализовано.** Желаемая ревизия и ACK устройства;
   после первого сохранения владельцем файловая публикация блокируется сервером.
   Старому агенту требуется обновление для получения таких политик.
8. **Присутствие.** Определить heartbeat/lease и пороги состояний «онлайн»,
   «нет связи», «данные устарели»; отсутствие ответа на P2P не заменяет их.
9. **Короткий адрес — решено.** Используется HTTPS на 443, явно указанный порт сохраняется.
10. **Открытие панели и локальная сессия.** Определить интеграцию с запуском
    приложения и установщиком, чтобы не требовать CLI для доступа к панели.
11. **Надёжность регистрации — реализовано.** Секреты с 256 битами случайности
    сохраняются агентом до запроса; повтор с тем же секретом идемпотентен.

## 13. Критерии приёмки

### Подключение и восстановление

- На чистом установленном клиенте пользователь проходит регистрацию только
  через панель; агент сам создаёт ключ и состояние, ручные файлы не нужны.
- Первое подключение с существующим пользовательским токеном требует адрес
  координатора и токен; если устройство новое, панель предлагает его имя.
- Второе собственное устройство попадает в тот же аккаунт, а не в новый.
- Повторный вход/обновление страницы не создаёт дубликатов и не меняет ключ.
- Ошибка после создания аккаунта не теряет выданный токен и не запускает
  повторное создание аккаунта как единственный вариант продолжения.
- Неверный токен, недоступный сервер и ошибка TLS имеют разные понятные состояния.
- Самоподписанный сертификат можно явно доверить через интерфейс без CLI
  и без отключения проверки TLS.
- Попытка входа в другую сеть отклоняется и не повреждает текущий профиль.

### Устройства, разрешения и карта

- Все собственные устройства видны независимо от наличия разрешений и активности.
- Два устройства одного владельца без явного разрешения не передают трафик.
- Доступ коллеге к порту сервера не открывает порты телефона владельца.
- Владелец меняет разрешения удалённого своего устройства через панель;
  подмена ID на чужое устройство отклоняется сервером.
- Выключенное устройство показывает «сохранено, ожидает устройства», а после
  возвращения подтверждает конкретную применённую ревизию.
- Два редактора не перезаписывают политики друг друга без обнаружения конфликта.
- Отзыв не показывается применённым до подтверждения/соответствующего ограничения
  срока действия старого доступа.
- Массовое распространение выполняется только по отдельному выбору и показывает
  отдельные результаты; новые устройства не наследуют его автоматически.
- Карта показывает направление и порты доступа; состояние непроверенного ребра
  не выглядит как установленное соединение.

### P2P и границы доступа

- Соединение инициируется именно от текущего локального устройства.
- При выданном доступе на целевой стороне нет диалога human approval.
- Принятый координатором запрос не отображается как подтверждённый прямой путь.
- При отзыве во время попытки не устанавливается более не разрешённый доступ.
- Потеря координатора, локального агента и прямого пути различимы в интерфейсе.
- Обычные снимки, URL входа в сеть, логи и сообщения ошибок не раскрывают секреты.
- Будущая панель без агента может управлять аккаунтом, но не обещает локальное
  WireGuard-соединение из одного браузера.

Главный раздел «Устройства» объединяет состояние сети, управление подключением,
поиск и список устройств. Отдельного раздела «Обзор» и повторного списка карточек
нет; старые ссылки `#overview` открывают «Устройства».
