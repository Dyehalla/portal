# План удалённого File Explorer для Portal

## Цель и границы

Добавить в локальную веб-панель Portal обозреватель файлов удалённого
зарегистрированного устройства. Пользователь должен видеть разрешённую
файловую область, переходить по каталогам, скачивать и загружать файлы,
создавать каталоги, переименовывать и удалять объекты.

Первая версия работает только в управляемом Linux-режиме и только по
подтверждённому прямому P2P-пути Portal. Координатор выдаёт карту, lease и
политику, но не пересылает содержимое файлов. Файлы не проходят через
браузерный сервер координатора и не попадают в логи.

Терминальный доступ и File Explorer остаются разными возможностями. Наличие
`terminal` не включает доступ к файлам, а File Explorer не даёт shell,
forwarding или выполнение команд.

## Архитектура

Поток операции выглядит так:

1. Браузер отправляет стандартные WebDAV-запросы в loopback API локального
   агента с уже существующим bearer-токеном.
2. Локальный API на каждом запросе проверяет snapshot, lease, прямой путь и
   `files`-разрешение.
3. Runtime локального устройства проксирует HTTP/WebDAV к выделенному порту на
   виртуальном IPv4/IPv6-адресе цели.
4. Runtime целевого устройства принимает запрос только на виртуальных адресах,
   запускает WebDAV-сервис под непривилегированным системным пользователем и
   ограничивает операции настроенным корнем файловой системы.

В качестве транспорта используется существующий WireGuard/TUN и P2P-проверка.
Новый relay и новый канал через координатор не добавляются. Самодельный
бинарный протокол не нужен: WebDAV уже задаёт операции каталогов, метаданные,
диапазоны, загрузку и удаление.

## Этап 0. Зафиксировать контракт и конфигурацию

Добавить в `runtime/src/config.rs` секцию, например:

```json
{
  "files": {
    "enabled": true,
    "listen_port": 2223,
    "root_dir": "/srv/portal-files",
    "user": "portal-files",
    "read_only": false,
    "max_connections": 4,
    "idle_timeout_seconds": 900,
    "max_file_size": 10737418240
  }
}
```

Обязательные правила конфигурации:

- `root_dir` должен быть абсолютным каталогом, созданным администратором;
- сервис не работает от root и не следует за symlink за пределы `root_dir`;
- `read_only` позволяет безопасно включить только просмотр и скачивание;
- порт File Service отделён от порта `sshd` и не публикуется на LAN/WAN;
- лимиты сессий, размера файла, размера чанка и времени простоя проверяются до
  запуска сервиса;
- относительные пути JSON-конфигурации разрешаются так же, как в существующем
  `FileConfig`.

В snapshot добавить только безопасное состояние сервиса: `enabled`, порт,
режим `read_only`, статус и последнюю ошибку. `root_dir`, реальные локальные
пути и содержимое каталогов в snapshot не возвращаются.

## Этап 1. Модель доступа и сетевой ACL

Ввести независимое поле `files: bool` в `PeerPermissions` и запросах доступа.
Старые JSON-политики без поля должны означать `files: false`.

Изменения:

- `net/src/model.rs` — `PeerPermissions`, `RequestAccess`, `AccessRequest`;
- `net/src/policy.rs` — нормализация, валидация сигналов и компиляция dedicated
  File Service port;
- `coordinator/src/store/schema.rs` и store-модули — миграция и сохранение
  ревизий;
- `coordinator/src/api.rs` — выдача, принятие и отзыв file-доступа;
- `runtime/src/managed.rs` и `runtime/src/runtime.rs` — применение политики;
- `runtime/src/snapshot.rs` — отображение направления `files`.

Порт является только транспортным механизмом. Авторизацией считается именно
`files`-право для конкретной пары устройств; смена порта не должна менять
смысл разрешения. При отзыве права новые TCP-сеансы блокируются тем же gate,
который уже закрывает TCP ACL и terminal.

В веб-редакторе политики добавить отдельную галочку «Файлы». Запрос доступа
должен явно показывать, что он разрешает просмотр/передачу файлов, и не должен
автоматически включать `tcp` или `terminal`.

## Этап 2. WebDAV-сервис на целевом агенте

Создать `runtime/src/file_service/` как lifecycle-обёртку над WebDAV-сервером.
Не нужно придумывать собственный wire-протокол: сервис обрабатывает стандартные
методы `OPTIONS`, `PROPFIND`, `GET`, `HEAD`, `PUT`, `MKCOL`, `MOVE`, `DELETE`, а
для первой версии не реализует `LOCK`/`UNLOCK`.

WebDAV слушает только виртуальные адреса Portal и отдельный порт `listen_port`.
Сетевой ACL проверяет `files` до того, как запрос попадёт в WebDAV. Сервис
работает от `user`, публикует один `root_dir` и не принимает произвольный путь
к файловой системе. `read_only` отключает `PUT`, `MKCOL`, `MOVE` и `DELETE`.

Ограничения WebDAV:

- путь запроса — только относительный путь внутри `root_dir`;
- `PROPFIND` ограничивается фиксированной глубиной и размером ответа;
- `GET` поддерживает `Range`, `HEAD` возвращает только безопасные метаданные;
- `PUT` выполняется во временный файл с атомарным rename после проверки размера;
- рекурсивное удаление, архивы, симлинки, специальные файлы, сокеты и device
  nodes запрещены;
- таймауты, лимиты размера тела и число одновременных запросов задаются runtime.

Для защиты от обхода каталога использовать Linux `openat2` с
`RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS` либо эквивалентный компонент с файловыми
дескрипторами и `O_NOFOLLOW`. Проверка через один `canonicalize` без защиты от
гонки недостаточна. Все операции выполняются относительно дескриптора корня.

## Этап 3. Same-origin WebDAV proxy

Добавить в локальный API маршрут вида
`/api/v1/files/{device_id}/{*path}`, принимающий WebDAV-методы и проксирующий
их на WebDAV-порт цели. Для proxy достаточно уже существующего bearer-токена
локального API; отдельный WebSocket и билет не нужны.

Перед каждым запросом proxy проверяет managed mode, целевой `device_id`, свежий
lease, `files == true`, состояние `direct` и виртуальный адрес. При отзыве
разрешения или потере lease новые запросы блокируются, а текущий TCP-stream
закрывается. Proxy должен потоково передавать body и response без загрузки
файла целиком в память, ограничивать размеры и таймауты и удалять из ошибок
внутренние пути цели.

Прямой WebDAV-доступ к виртуальному порту можно оставить для native-клиентов,
но MVP веб-панели использует только same-origin proxy: это исключает CORS,
утечки токена и смешение локального HTTP с удалённым адресом.

## Этап 4. Веб-панель

Добавить страницу `#files` рядом с уже существующим `#terminal`:

- выбор устройства с `files`-разрешением;
- хлебные крошки и постраничная таблица каталогов;
- действия открыть, скачать, загрузить, создать каталог, переименовать,
  удалить через `PROPFIND`/`GET`/`PUT`/`MKCOL`/`MOVE`/`DELETE`;
- drag-and-drop и индикатор прогресса для загрузок;
- подтверждение удаления, предупреждение о конфликте и повтор загрузки;
- состояния `starting`, `connected`, `stale`, `denied`, `offline`, `closed`;
- восстановление только списка каталога после обновления страницы, без хранения
  credentials и содержимого в `localStorage`.

В `runtime/web/app.js` переиспользовать выбор устройств, snapshot и механизм
обновления политики. Для каталога использовать XML-парсер WebDAV и обычные
`fetch` с нужными HTTP-методами. Все frontend-ресурсы остаются локальными и
встраиваются в бинарник runtime, как текущие `app.js`, `xterm.js` и `xterm.css`.

## Этап 5. Проверки и эксплуатация

### Unit-тесты

- нормализация WebDAV-путей и запрет обхода через `..`, symlink и race;
- права на корень и временные файлы;
- атомарный commit загрузки и очистка незавершённых загрузок;
- постраничная выдача и стабильная сортировка имён;
- лимиты тела, файла, глубины `PROPFIND`, одновременных запросов и таймаутов;
- сериализация старых политик без `files`;
- корректное преобразование WebDAV-ошибок `403`, `404`, `409`, `413`, `423`, `507`.

### Интеграционные сценарии

Расширить namespace-сценарий рядом с `runtime/scripts/check-managed.py`:

1. два зарегистрированных агента получают прямой путь;
2. владелец выдаёт только `files`;
3. браузерный WebDAV proxy получает список, скачивает файл и загружает его обратно;
4. `terminal` и произвольный TCP-порт без соответствующих прав остаются
   закрытыми;
5. отзыв права блокирует новые запросы и текущий proxy после следующей проверки;
6. IPv4 и IPv6 дают одинаковый результат;
7. offline, истёкший lease и отсутствие прямого пути дают понятные статусы;
8. перезапуск runtime не раскрывает временные файлы и сохраняет только
   администраторскую конфигурацию.

### Безопасность и эксплуатация

- проверить запуск от непривилегированного пользователя и отсутствие доступа к
  `/etc`, `/proc`, сокетам и соседним каталогам;
- проверить, что File Service слушает только виртуальные адреса;
- добавить rate limiting на операции и метрики счётчиков без путей и содержимого;
- задокументировать рекомендуемые права каталога (`0700`/`0750`) и резервное
  копирование;
- добавить понятные сообщения в `status`, snapshot и журнал только о состоянии
  сервиса.

## Критерии готовности MVP

MVP готов, когда два Linux-агента в одной сети Portal могут по прямому P2P-пути
открыть File Explorer в браузере, получить список и скачать/загрузить файл
только при отдельном `files`-разрешении; при отзыве разрешения, истечении lease,
попытке обхода `root_dir` или недоступном пути
операция блокируется; существующие WireGuard, TCP ACL, terminal и P2P-тесты
продолжают проходить.
