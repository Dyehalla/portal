# План удалённого терминала Portal

## Цель

Добавить в Portal удалённый терминал между зарегистрированными устройствами.
На первой итерации Portal сам запускает `sshd`, а подключение выполняется из
терминала операционной системы обычной командой `ssh`. На второй итерации тот же
SSH-сервис используется из встроенной веб-панели.

Транспортом остаётся существующий WireGuard-туннель Portal. Координатор выдаёт
идентичность устройства, карту сети и разрешение; содержимое SSH-сессии через
координатор не проходит.

## Что уже есть в проекте

- WireGuard/TUN и управление пирами в `wireguard/`;
- управляемый Linux-агент в `runtime/`;
- HTTPS-координатор, реестр устройств и TCP-политики в `coordinator/` и `net/`;
- P2P hole punching и проверка прямого пути;
- локальный CLI и веб-панель.

Сейчас Portal умеет ограничивать TCP-доступ по портам, но не запускает SSH-сервис
и не управляет ключами или учётными записями SSH. Relay отсутствует, поэтому на
первой версии терминал работает только при доступном прямом P2P-пути.

## Решения первой итерации

1. Поддерживается Linux.
2. При `portal start` целевой агент Portal сам запускает `sshd` как дочерний
   foreground-процесс и сам отвечает за его остановку и перезапуск. Отдельная
   systemd-служба для `sshd` в первой версии не используется.
3. `sshd` слушает только виртуальный адрес Portal и отдельный порт, по умолчанию
   `2222`. Публичный LAN/WAN-интерфейс и loopback не используются.
4. Подключение выполняется стандартным клиентом:

   ```sh
   ssh -p 2222 USER@PORTAL_VIRTUAL_IP
   ```

5. Доступ к SSH является отдельным разрешением устройства. Наличие записи в
   реестре или принадлежность одному владельцу доступа не дают.
6. Координатор не пересылает SSH-трафик и не получает пароли, приватные ключи,
   команды или вывод терминала.
7. На первой итерации Portal не реализует собственный SSH-протокол, браузерный
   терминал, relay и передачу произвольных команд через HTTP API.

## Итерация 1: SSH из терминала

### 1. Зафиксировать конфигурацию SSH

Добавить в конфигурацию runtime секцию терминала:

```json
{
  "terminal": {
    "enabled": true,
    "listen_port": 2222,
    "user": "portal",
    "authorized_keys_file": "/etc/portal/authorized_keys",
    "host_key_dir": "/etc/portal/ssh"
  }
}
```

Конкретную схему полей нужно согласовать с текущими значениями по умолчанию.
Обязательные свойства:

- явное включение/выключение SSH;
- порт и виртуальный адрес прослушивания;
- системный пользователь, от которого запускается shell;
- каталог host keys;
- файл или каталог `authorized_keys`;
- лимиты числа сессий и времени простоя.

Host keys создаются один раз с правами `0600` и сохраняются между перезапусками.
Приватные ключи клиентов Portal на целевом устройстве не создаются и не
передаются координатору.

После получения карты сети и назначения виртуального адреса Portal запускает:

```sh
sshd -D -e -f /run/portal/sshd_config
```

Для диагностики можно предусмотреть отдельный режим `portal sshd`, но штатный
путь — запуск вместе с `portal start`/`portal run`.

### 2. Запуск и остановка `sshd`

Добавить отдельный lifecycle-компонент в `runtime`, владеющий дочерним процессом
`sshd`:

- проверить наличие поддерживаемого `sshd`;
- проверить конфигурацию командой `sshd -t` до открытия порта;
- подготовить временный или постоянный конфигурационный файл;
- запустить `sshd` в foreground-режиме под supervisor Portal после настройки TUN;
- передать сигналы и корректно завершить дочерний процесс;
- перезапустить сервис после контролируемого падения с ограничением частоты;
- не запускать второй `sshd` при повторном старте runtime.

Рекомендуемые ограничения конфигурации OpenSSH:

- `PasswordAuthentication no`;
- `PermitRootLogin no`;
- `AllowTcpForwarding no`;
- `X11Forwarding no`;
- `PermitTunnel no`;
- ограниченный `MaxSessions`;
- `ClientAliveInterval` и `ClientAliveCountMax`;
- явный `ForceCommand` или allowlist shell, если продукт не должен давать
  полноценный shell.

Для первой версии используется системный `/usr/sbin/sshd`; Portal проверяет его
наличие, версию и конфигурацию до запуска. Сборка и поставка собственного
OpenSSH остаются отдельной задачей.

### 3. Модель доступа Portal

В существующую модель TCP-политик добавить отдельный признак терминального
доступа либо зарезервированный сервис `terminal`. Не полагаться только на номер
порта: это позволит позже сменить порт без изменения смысла разрешения.

Изменить:

- `net/src/model.rs` — модель разрешения;
- `net/src/policy.rs` — проверка и компиляция политики;
- `coordinator/src/store/schema.rs` — миграция SQLite;
- `coordinator/src/store/policy.rs` — хранение ревизий и ACK;
- `coordinator/src/store/access_requests.rs` — запрос терминального доступа;
- `coordinator/src/api.rs` — API выдачи, принятия и отзыва доступа;
- `runtime/src/managed.rs` — применение разрешения на устройстве.

Существующие TCP-разрешения должны продолжить работать. Для совместимости
нужна миграция старых политик и однозначное поведение при отсутствии поля
`terminal`.

### 4. CLI-сценарий

Добавить команду:

```sh
portal terminal --device-id DEVICE_ID [--user USER]
```

Команда должна:

1. запросить у локального runtime актуальный снимок;
2. найти виртуальный IPv4/IPv6-адрес целевого устройства;
3. проверить действующую карту, lease, разрешение терминала и состояние пути;
4. при необходимости инициировать существующий `connect`/P2P probe;
5. заменить себя на `ssh` или запустить его с корректным stdin/stdout/stderr;
6. вернуть код завершения SSH-сессии;
7. различать ошибки доступа, истёкшей карты, отсутствующего `sshd`, offline и
   недоступного прямого пути.

Изменить:

- `cli/src/main.rs`;
- `cli/src/http_api.rs`;
- `runtime/src/api.rs` — только команды проверки и открытия разрешённого
  терминального подключения;
- `runtime/src/snapshot.rs` — статус SSH-сервиса и терминального разрешения.

Portal не должен принимать удалённую команду в JSON вроде `exec: "..."`. Вся
командная строка должна проходить через обычный SSH-сеанс и его аутентификацию.

### 5. Управление SSH-ключами

Нужно определить минимальный поток первой версии:

- пользователь сам добавляет публичный ключ в `authorized_keys` на целевом
  устройстве;
- либо Portal хранит управляемый список публичных ключей устройства и обновляет
  его через координатор;
- приватный ключ всегда остаётся на клиентском устройстве;
- в логах не появляются содержимое ключей и пароли.

Для первого прототипа допустим локальный `authorized_keys_file`, но production-
вариант должен иметь безопасное управление ключами через панель аккаунта или
административный provisioning-механизм.

### 6. Проверки первой итерации

Добавить тесты и сценарии:

- `sshd` запускается при старте runtime и завершается вместе с ним;
- повторный запуск не создаёт второй процесс и не меняет host key;
- подключение по IPv4 и IPv6 через виртуальный адрес;
- подключение без разрешения отклоняется;
- отзыв разрешения запрещает новые подключения;
- истёкшая карта блокирует терминал;
- `PermitRootLogin`, парольная аутентификация и forwarding запрещены;
- неизвестный пользователь и неверный ключ получают отказ;
- завершение SSH возвращает ожидаемый exit status;
- падение `sshd` видно в `status`, snapshot и журнале runtime;
- устройство за недоступным NAT показывает понятную ошибку прямого пути.

Основной интеграционный сценарий следует добавить в существующую проверку
изолированных namespace рядом с `runtime/scripts/check-managed.py`: координатор,
два агента, `sshd` на втором агенте и SSH-подключение с первого.

## Итерация 2: терминал в браузере

Вторая итерация не меняет SSH-сервис на целевом устройстве. Она добавляет
клиентский шлюз в локальный Portal:

1. Веб-панель через локальный API создаёт короткую терминальную сессию.
2. Браузер открывает WebSocket только с локальным агентом.
3. Агент запускает локальный `ssh` с PTY к виртуальному адресу цели.
4. Байтовые потоки stdin/stdout/stderr передаются между PTY и WebSocket.
5. События resize, Ctrl-C, закрытие и exit status передаются явно.

Для этого понадобятся:

- WebSocket-маршрут в `runtime/src/api.rs`;
- supervisor PTY-процессов в `runtime/src/terminal/`;
- короткоживущий одноразовый session ticket, не передаваемый в URL;
- вкладка терминала в `runtime/web/index.html` и `runtime/web/app.js`;
- локально собранный `xterm.js` без CDN;
- ограничения буферов, idle timeout и число одновременных сессий;
- отображение статусов `starting`, `connected`, `stale`, `closed`, `denied`.

Веб-клиент не должен получать приватный WireGuard-ключ, device token или
пользовательский токен координатора.

## Сквозные требования безопасности

- `sshd` слушает только виртуальный интерфейс Portal;
- пользователь shell не является root;
- доступ к терминалу выдаётся конкретной паре устройств;
- координатор не является data-plane и не видит содержимое сессий;
- токены не попадают в URL, snapshot, журналы и сообщения об ошибках;
- политика и lease проверяются до открытия сессии;
- закрытие/отзыв доступа не оставляет новые разрешённые подключения;
- stdout, stdin и команды терминала не записываются без отдельного явного
  режима аудита.

## Критерии готовности первой версии

Первая версия считается готовой, когда:

1. два агента зарегистрированы в одной сети;
2. второй агент автоматически запускает ограниченный `sshd`;
3. владелец выдаёт первому устройству терминальное разрешение;
4. `portal terminal --device-id ...` устанавливает интерактивную SSH-сессию;
5. соединение работает по IPv4/IPv6 через Portal;
6. отказ, отзыв, истечение lease и остановка `sshd` корректно отражаются в CLI;
7. существующие WireGuard, P2P и TCP ACL-тесты продолжают проходить.
